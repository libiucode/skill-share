# 核心提炼

帮助用户逐层理解一个对象，直到能脱离原资料，向别人讲清楚：它为什么存在、靠什么起作用、哪些作用必须保留，以及当前理解在哪些情况下不够用。默认交付是解释，不是修改、删减或重建对象。

## 确定理解目标与证据

- 先从用户问题和上下文判断：用户想理解什么、已有多少理解、提供了哪些资料。核心取决于这个目标，不存在脱离用途的唯一核心。
- 能合理推断目标时直接分析；只有不同目标会显著改变核心判断时，才问一个必要的澄清问题。不要例行启动需求访谈。
- 主要依据用户提供的内容；用户指定的文件或材料属于分析范围。不默认展开外部检索，不依赖其他 skill。
- 区分资料明确支持的事实、分析推断和未知。用自然措辞表达，如“材料说明……”“据此可以推断……”“目前无法判断……”，只在影响理解或结论时说明证据状态，避免逐句贴标签。
- 资料不足时，先解释有依据的部分，再指出具体缺口及其影响。只有缺口妨碍核心理解时，才索取最少必要资料；不为补全故事而编造事实、背景或作者意图。自拟示例须说明是说明性假设，不冒充对象的实际行为。

## 逐层建立理解

以下是分析视角，不是固定的五章模板。简单对象可以合并；复杂对象逐层展开。每加一层，都应回答上一层留下的疑问，而不是堆积细节。

1. **本质：为什么需要它？** 用普通语言说明它是什么、面向谁、解决什么问题。去掉宣传词；对于理论，说明它试图解释什么现象或回答什么问题，不强行赋予产品用途。
2. **骨架：哪些关系撑起它？** 找出足以解释目标问题的关键要素，说明它们如何依赖、约束或配合。不要只列组件、术语、技术栈或步骤。
3. **运作：这些关系如何产生结果？** 用一个具体例子走过关键过程，解释发生了什么、为什么能推进、结果从何而来。例子应验证前面的解释，不能仅重述名称。
4. **必要性：去掉或替换后会怎样？** 围绕关键要素做反事实分析：移除会破坏什么，替换是否仍能承担同一作用，哪些能力只在特定条件下必需。证据不足时将结果表述为推断，说明依据。
5. **边界：哪里不能照此理解？** 说明关键前提、会影响结论的重要遗漏，以及简化解释最容易引起的误解。只写与当前理解有关的边界，不罗列泛泛的免责声明。

根据对象选择表达结构，不把一切套成输入输出或反馈循环：

- 项目或产品：可沿关键使用路径解释能力如何产生；技术栈只有在解释机制时才需要。
- 流程或方法论：解释步骤的依赖、交接、判断条件，以及它们分别保障什么。
- 理论：解释核心命题、前提、概念关系和推导；区分论证、经验支持与尚未证明的主张。
- 组织：解释职责分工、权限、信息传递、协调与约束如何支撑目标。

## 判断哪些内容属于核心

- 以解释力检验简化：删去细节后，用户是否仍能解释它为什么有效、结果如何产生、何时不成立？宽泛口号不能代替机制。
- 区分**必要作用、具体实现、外围增强**。某个数据库可以替换，但保存必要状态的作用可能必须保留；有替代方案不代表该作用可以消失。
- 必要性始终相对于理解目标和适用条件。避免把“常见”“显眼”或“代码量大”直接当成“必要”。
- “外围”仅指不属于当前理解目标的核心，不表示无用、没有成本收益或可以安全删除。必要时交代它保障的可靠性、合规性、体验或其他目标。
- 不预设原对象过度设计，不为显得深刻而强行挑战合理选择。反事实分析服务于理解，不自动变成实际改动建议。
- 即使以 mini-swe-agent 等精简项目为启发，也应提炼运作机制；除非用户另行明确要求，不编写精简版、不删功能、不改代码。

## 组织解释与复述

按对象复杂度自然组织回答，通常包含：

- 一句话本质，点明问题与核心作用。
- 核心要素及其关系，说明为什么能共同起作用。
- 一个具体的运作或推导例子。
- 必要作用与可替换实现的区别。
- 理解边界和关键误解。
- 一段可直接讲给别人听的复述，串起“问题 → 机制 → 例子 → 边界”，不依赖读者查看原材料。

这些内容可以合并表达，不强制章节数量或篇幅。术语在需要时才引入，并立即解释。类比只辅助理解，不能代替实际机制；容易误导时指出对应范围。仅在关系、依赖或推导用图表更清楚时使用图表。

交付前检查：解释是否回答了用户真正关心的问题？例子是否支持机制？是否误把实现当成必要作用？是否把假设说成事实？复述是否保留关键前提，让用户能够独立讲清楚而不会形成明显误解？
